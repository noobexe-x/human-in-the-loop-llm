## 3. データ・基盤層（研究中）

### 3.1 Web との違い（なぜ「基盤」に関心があるか）

- **Web（ToC）:** 障害はユーザー報告・HTTP エラー・監視アラートで比較的早く気づける。
- **データプラットフォーム:** パイプラインや品質の劣化は **サイレント** に進みやすい（数値のずれ、重複、口径変更、AI が誤った正例を学ぶ等）。
- ローカル PoC では再現しにくいが、本番では **可観測性・分层・再実行** が重要になる、という理解。

### 3.2 資料を読んで得た理解（要約）

課題着手時に読んだ dev.to 記事（Data Platform 構成、ETL 入門、AEO/GEO/LLMO）および LLM 学習の全体像資料を踏まえ、現時点では次のように整理している。

- **Data Platform** は、MATLAB や Python で都度分析して表を出す、というイメージとは異なり、データが **流れ続け・積み上がり・インフラ上で受け止められる** もの、という説明が多い。今回 demo の「判定を DB に残し、次回 Prompt に使う」は、その最小版の挙動に近い。
- データ量やソースが増えると、生データをそのままアプリが直接読む形では破綻しやすい。**段階ごとに信頼性と用途を分ける（分层）** 必要がある、という説明が繰り返し出てくる。Web 開発の MVC のように、「型」として捉えると理解しやすい、という比喩も見た。

- **ETL** の入門では、Extract / Transform / Load を **パイプライン** として設計・運用する話が中心だった。今回 demo の `etl_service`（文字清洗・候補の重複排除など）はその縮小版であり、本番では **再実行・監視・品質ルール** がセットで必要になる、という理解に至った。
- **LLMO / RAG** 関連では、Vector DB や検索拡張は有用だが、**いきなり検索基盤を足す前に、何を正例・負例として残すか**（今回の 4 段階判定とコンテンツライブラリ）が先、という順序感を得た。図上の Qdrant や LightGBM は、閉ループの「芯」が動いてからでも遅くない、と判断している。
- 本番では、ローカル検証だけでは見えにくい **リソース配分・突発的な流量・タイムアウトとリトライ** が、パイプライン全体の安定性を左右する、という記述も多い。未経験のため実感はないが、「基盤・運用」の課題として認識しておく。

以上は **提出 demo には未実装** である。用語と方向性のメモであり、数倉や Medallion を短期間で構築する計画ではない。
